## What T03 delivers

### Key Vault and customer-managed keys (`infra/azure/modules/key-vault.bicep`)

One Premium vault in Canada Central: Azure RBAC authorization only (no access
policies), soft delete with 90-day retention **and** purge protection, public
network access disabled, deny-default firewall (trusted Azure services allowed,
as the SQL TDE and Storage CMK integrations require behind a firewall), no
deployment/disk/template access. Four purpose-separated RSA-HSM 3072 keys, each
non-exportable, `keyOps` wrap/unwrap only, with a Key Vault rotation policy that
rotates at `P90D`:

| Key | Purpose | Reached by |
|---|---|---|
| runtime `sourceEnvelopeKeyName` | per-content data keys (consumed by T04) | Portal identity, wrap/unwrap on this key only |
| runtime `dataProtectionKeyName` | shared key ring | Portal identity, wrap/unwrap on this key only |
| `sql-tde-protector` | SQL TDE | dedicated SQL TDE identity only |
| `source-blob-cmk` | source Blob service encryption (bound by T04) | granted by T04's storage module |

The Portal identity also gets Secrets User on exactly the two intake secrets
(declared `existing`, so deployment fails before they are provisioned instead of
granting a vault-wide role). Secret values never appear in the repository.

### Exact-version wrap/unwrap (`Keys/KeyVaultContentKeyWrapper.cs`)

RSA-OAEP-256 over a **versionless** key: a wrap uses the current version and
records the exact versioned key identifier Key Vault reports; an unwrap is sent
**only** to that recorded version — never silently forward to the current one.
A wrapped key naming another vault, another key, no version, a malformed version
or another algorithm is refused before any call. Every failure (wrong identity,
disabled/missing key, tamper, untrusted TLS certificate) is one fixed
`CryptographicException` with no inner exception and no value.

### Retirement, rotation and revocation (`Keys/KeyVersionUsageGuard.cs`)

Pure and clock-free. Retirement of a version is permitted only when it is not the
active version and exactly one complete, current (≤ 24 h, not future-dated)
inventory from **each** of retained ciphertext, the Data Protection key ring and
recoverable backups references nothing of it. Missing, duplicated, incomplete,
stale, malformed or unknown-source evidence refuses. Emergency revocation needs
just-in-time elevation (never standing access), a closed justification with a
reference, a reviewer distinct from the requester, and a window of at most 8 h
containing the decision. The rotation target is exactly `P90D`.

### Data Protection key ring (`Protection/AzureDataProtectionConfiguration.cs`, `key-ring-storage.bicep`)

Production registers the Azure Blob repository (`<container>/key-ring.xml`) plus
the Azure Key Vault encryptor, over the configured user-assigned managed
identity, with the production application discriminator and a 90-day key
lifetime. The gate accepts only that exact repository/encryptor pair with the
approved discriminator. Storage: a dedicated control account (separate from
source content), Canadian GZRS, Entra-only (shared key, SAS and anonymous access
off), HTTPS/TLS 1.2, infrastructure encryption, public access disabled, blob
versioning and 30-day blob/container soft delete, container-scoped Blob Data
Contributor for the Portal identity. The ring holds only Key Vault-wrapped keys
(tested: no `<masterKey` element is ever stored).

### Production credential loading (`Keys/KeyVaultRuntimeMaterialProvider.cs`, Portal)

In Production the composition root loads `taxai-intake-digest-key` and
`taxai-intake-fingerprint-key` once, by managed identity, bounded by the probe
deadline, and only after the profile's identity, vault binding and deadline are
structurally valid. Missing, disabled, not-yet-valid, expired, non-canonical or
shared material is refused with no material. Loaded material is placed only in
the in-memory configuration the **unchanged** `IntakeConfiguration` validates
(nothing is persisted, logged or rendered). Plaintext
`TaxAi:Intake:DigestKey`/`FingerprintKey` settings are never loaded over, and
the gate refuses them (`UnapprovedConfigurationEntry`). A refused load leaves no
material and intake validation refuses startup with its fixed message.

### SQL (`sql.bicep`, `SqlConnectionStringGuard.cs`)

Azure SQL logical server in Canada Central: Entra-only authentication with a
dedicated migration identity as administrator, public access disabled,
outbound restricted, TLS 1.2 minimum, zone-redundant database, TDE with the
Key Vault CMK through a dedicated SQL identity and an auto-rotating encryption
protector. The connection guard (unchanged signature) now also refuses every
Entra mode except managed identity (stored password, service principal,
interactive, device code, default chain, integrated, workload identity), a
managed identity with a password or integrated security,
`HostNameInCertificate` overrides and `Persist Security Info=True`, in addition
to the existing encryption and `TrustServerCertificate` rules.

### Admission-gate additions (`ProductionAdmissionGate.cs`)

1. The key ring must be exactly the Azure Blob repository + Azure Key Vault
   encryptor with the approved discriminator (`DurableDataProtectionMissing`).
2. Intake material must equal the vault-loaded material
   (`UnapprovedConfigurationEntry`).
3. After the identity is verified, `IApprovedResourceProbe` must find both
   wrapping keys enabled, RSA ≥ 3072, wrap/unwrap, purge-protected and
   non-exportable, both actually wrapping, and the key ring round-tripping,
   within the probe deadline (`SourceEnvelopeEncryptionMissing`,
   `DataProtectionConfigurationMissing`, `DurableDataProtectionMissing`,
   `KeyVaultBindingInvalid`, `InfrastructureValidationUnregistered`).
   A stalled probe is unverifiable, never a pass.

No new `TaxAi:Production:*` setting exists. With every T01–T03 rule satisfied,
the complete synthetic profile still refuses on exactly the three later-slice
adapters, and evidence (including DEP-14) keeps it refused.

### Sixth private endpoint (rationale)

T02's `private-endpoints.bicep` binds exactly five endpoints (Portal plus the
four approved dependencies) and its guards still hold unchanged. The key-ring
store is a new, separate control account that the architecture requires to be
private, so `key-ring-storage.bicep` adds its own endpoint (`<prefix>-pe-keyring`,
group `blob`) bound to the existing blob private DNS zone. It is an explicit T03
addition, not a change to the five-binding guarantee; no T02 guard rejected it
and none was edited. The dependency allowlist is unchanged (the key ring needs
no egress).
