## What T04 delivers

### Authenticated envelope (`Content/SourceEnvelopeCodec.cs`)

A fresh random 256-bit data key per content. The plaintext is split into
64 KiB chunks, each sealed with the platform AES-256-GCM; the 96-bit nonce is a
random 8-byte prefix plus the 4-byte chunk index, and each chunk's associated
data binds the format magic, the firm, the case, the opaque resource
identifier, the chunk index, its length and its final flag. Truncation,
reordering, duplication, extension, a cleared final flag, header or length
tampering and every scope or key substitution fail authentication. Decryption
measures and authenticates the complete bounded ciphertext before releasing any
plaintext, and every failure is one fixed `CryptographicException`. No novel
primitive. The data key is wrapped by T03's `KeyVaultContentKeyWrapper`
(RSA-OAEP-256, exact recorded version) and stored in a **separate key
envelope** that names its scope, so a rotation can rewrap it without rewriting
the upload-once source object.

### Write-only production store (`Content/AzureIntakeContentStore.cs`)

1. The registry row is committed (`Staged`) **before** any storage allocation.
2. A fresh data key is wrapped and the key envelope is written upload-once.
3. Plaintext is streamed one 64 KiB chunk at a time into bounded 4 MiB staged
   blocks of ciphertext — never a file — while the scoped keyed fingerprint
   (the same HKDF/HMAC scoping the intake workflow compares) is computed.
4. The block list is committed with `If-None-Match: *`: an existing object is
   never overwritten (AC-027).
5. Any failure or cancellation records cleanup intent and deletes whatever was
   allocated within a finite budget; the caller sees one fixed refusal.

`DeleteIfExistsAsync` (the existing compensating-cleanup port) acts only on a
`Staged` or `PurgePending` registration of the trusted scope: an uncertain
metadata commit that actually bound the object never loses its source.
`CleanUpUncommittedAsync` replays pending cleanup and stale staged objects for
one trusted firm (orphan tracking and recovery replay). There is no read member,
URL, SAS or public access.

### Extraction-only reader (`Content/AzureExtractionContentReader.cs`)

A read requires a registry row **bound** to exactly the trusted firm, case,
committed document and content key, whose committed intake document still names
the same key (checked in one query). Only then are the two objects fetched —
each only if its reported length is within the bound — the key envelope checked
against the scope, the data key unwrapped by its recorded version, and the
complete ciphertext authenticated. Every mismatch, unbound or purged row,
tamper, transplant, oversize, missing object, unusable key or identity, and
storage failure returns null; cancellation propagates. The plaintext lives in
one in-memory buffer inside the lease and is cleared on disposal. The reader is
registered as its concrete type only, never as a general
`IExtractionContentReader`.

### Scoped physical deletion (`Content/AzureSourceObjectPurger.cs`)

Deletes one resource's ciphertext and key envelope (including any snapshot)
after checking that a present key envelope names exactly the expected scope,
then observes both absent from the primary. **It never reports completion it did
not observe:** the approved `Standard_GZRS` account gives the application no
read access to the Canada East secondary, so a verified primary deletion is
`Pending`, never `Complete`, and stays in the registry for replay. Due lifecycle
deletion and full-form destruction evidence are not invented here (T07/T08).

### Source registry (ClientIntake contract, Persistence adapter, migration)

- `ClientIntake`: `ISourceRegistryStore`, `ISourceObjectPurger`, the closed
  `SourceRegistryState` / `SourceRegistryWriteCode` / `SourceObjectPurgeOutcome`
  vocabularies and the immutable `SourceRegistration` (identifiers and key
  `[JsonIgnore]`, structural `ToString()`). Every member takes the trusted firm
  first and an explicit case. ClientIntake still implements none of its ports.
- `Persistence`: `SqlSourceRegistryStore`, one entity, one configuration and the
  additive migration `20260927000000_AddSourceRegistry` creating only
  `SourceRegistrations` (PK firm/case/resource; unique firm/case/content key;
  every index and foreign key leads with the firm; FKs to the intake case and,
  once bound, the committed intake document; four check constraints for the
  state machine). `SqlIntakeStore.AppendUploadAttemptAsync` binds the staged
  registration to the accepted document **inside the same serializable upload
  transaction**, after the document row is saved; if cleanup already took the
  object, the whole commit rolls back as a conflict. State changes are single
  conditional updates, so cleanup and a racing commit cannot both win. A commit
  with no registration at all (the Development filesystem store) is unchanged.

### Infrastructure (`infra/azure/modules/storage.bicep`, `main.bicep`, contract)

One standard GPv2 `Standard_GZRS` account in Canada Central; Entra-only (shared
key, local users, SAS, anonymous and cross-tenant access off), HTTPS/TLS 1.2,
public network access disabled with a deny-default firewall and **no**
trusted-service bypass, infrastructure encryption on, and service encryption
with the approved Key Vault `source-blob-cmk` key through a dedicated
user-assigned identity holding Crypto Service Encryption User on that one key
(versionless reference follows the 90-day rotation; AC-040). Blob versioning,
blob and container soft delete, change feed and point-in-time restore are
disabled; no immutability, legal hold, snapshot or lifecycle policy exists
(AC-029). One `taxai-source` container with `publicAccess: 'None'`; the Portal
identity has Storage Blob Data Contributor on that container only. The private
endpoint is T02's existing source-storage binding; `main.bicep` now makes the
dependency endpoints wait for the source account. The closed
`data-configuration.schema.json` gains `sourceStorage` and `sourceEnvelope`
sections, every value a constant.

  exactly `AzureIntakeContentStore`, and the reader only when exactly
  `AzureExtractionContentReader` is registered as its concrete type; a general

  wrapping key, identity or bound registers nothing and is refused.

  `x-ms-sku-name` / `x-ms-account-kind` headers. It writes, lists and reads no
  object. Findings map to `StorageBindingInvalid`.

  compensation budget.
